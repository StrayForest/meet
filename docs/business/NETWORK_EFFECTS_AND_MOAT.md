# Network effects and moat

## Desired flywheel
More quality physical supply → more useful discovery → more participants → richer privacy-safe social signals/Pods → higher confidence and conversion → more attendance → stronger trust/connection graph → more repeat/community supply → more organizer value → more quality supply.

## Negative loops to detect
- empty social graph → low join confidence → fewer joins → emptier graph;
- low-quality/stale events → failed attendance → uninstall/distrust;
- high no-show rate → weak group experience → organizer/user churn;
- overbroad city expansion → thin density everywhere;
- unsafe incidents → trust collapse → acquisition/retention damage;
- paid-growth masking → registrations rise while attendance/repeat stay flat.

Each negative loop needs a dashboard owner and an intervention/runbook once production data exists.

## Defensibility thesis
Event listings alone are not a moat. Long-term defensibility may emerge from the combined, privacy-governed graph of:
1. canonical local event/occurrence and organizer supply;
2. user interest/context and discovery outcomes;
3. participation and credible attendance outcomes;
4. trusted recurring co-attendance/connections and safety signals;
5. organizer performance/audience relationships;
6. learned ranking of what produces successful IRL participation.

The moat is **outcome data + local network density + trusted organizer/user relationships**, not proprietary infrastructure.

## Copyability test
For every major feature ask: if a large competitor copies the UI in 90 days, what remains unique? Acceptable answers are accumulated local liquidity/data/relationships/trust, not code complexity.

## Data responsibility
Never weaken privacy/safety to create a moat. Exact private locations, message bodies, KYC evidence and unrelated sensitive data are excluded from growth/ML defensibility strategy.
