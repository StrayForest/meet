# Network effects and moat

## Desired flywheel
More quality physical supply → more useful discovery → more participants → richer privacy-safe social signals/Pods → higher confidence and conversion → more attendance → stronger trust/connection graph → more repeat/community supply → more organizer value → more quality supply.

## Graph thesis
Long-term defensibility is not an event database. Subject to privacy/safety constraints, Meet can accumulate complementary graphs:
- **event graph:** canonical occurrences, places, categories and organizers;
- **attendance graph:** credible evidence of which opportunities produce real participation;
- **social graph:** repeated co-attendance/connections, not random follower counts;
- **trust graph:** safety/reliability signals appropriate for product use;
- **organization graph:** organizers, audiences and repeat local relationships.

The strategic question becomes not only `who knows whom?`, but **`who actually does things with whom, where, and in what activity context?`**. Ranking value comes from learning which opportunities reliably create successful IRL outcomes.

## Negative loops to detect
- empty social graph → low join confidence → fewer joins → emptier graph;
- low-quality/stale events → failed attendance → uninstall/distrust;
- high no-show rate → weak group experience → organizer/user churn;
- overbroad city expansion → thin density everywhere;
- unsafe incidents → trust collapse → acquisition/retention damage;
- paid-growth masking → registrations rise while attendance/repeat stay flat;
- founder seeding never declines → apparent liquidity is operationally subsidized rather than network-driven.

Each negative loop needs a dashboard owner and an intervention/runbook once production data exists.

## Defensibility thesis
Event listings alone are not a moat. Long-term defensibility may emerge from the combined, privacy-governed graph of:
1. canonical local event/occurrence and organizer supply;
2. user interest/context and discovery outcomes;
3. participation and credible attendance outcomes;
4. trusted recurring co-attendance/connections and safety signals;
5. organizer performance/audience relationships;
6. learned ranking of what produces successful IRL participation;
7. local distribution/SEO/community relationships that repeatedly replenish liquidity.

The moat is **outcome data + local network density + trusted organizer/user relationships + efficient distribution**, not proprietary infrastructure.

## Network-effect health
Measure whether value compounds:
- share of joins/attendance caused by existing Meet social proof;
- referral/invite contribution to successful participation;
- repeat co-attendance/connections;
- organizer repeat publishing/spend;
- share of priority occurrences that become socially active without manual seeding;
- time/cost to activate a second city/category compared with the first.

## Copyability test
For every major feature ask: if a large competitor copies the UI in 90 days, what remains unique? Acceptable answers are accumulated local liquidity/data/relationships/trust/distribution, not code complexity.

## Data responsibility
Never weaken privacy/safety to create a moat. Exact private locations, message bodies, KYC evidence and unrelated sensitive data are excluded from growth/ML defensibility strategy.
